# Project Constitution: Phase II – Full-Stack Todo Web Application

- **Version:** v2.0.0
- **Ratified:** 2026-01-03
- **Last Amended:** 2026-01-05
- **Surface:** Phase II – Full-Stack Todo Web Application (Spec-Kit Plus governed)

## 1. Project Identity
- **Project Name:** Phase II – Full-Stack Todo Web Application
- **Theme:** Elevate the Phase I CLI experience into a production-grade full-stack product without changing domain logic.
- **Development Style:** Specification-driven development (SDD) enforced through Spec-Kit Plus.
- **Workflow Enforcement:** Specify → Plan → Tasks → Implement → Review, with gate checks at every transition.
- **Execution Governance:** Claude Code CLI executing Spec-Kit Plus commands only.
- **Phase II Technology Stack:**
  - **UI Layer:** Next.js (App Router) with TypeScript, Server Actions, and React Server Components.
  - **API Layer:** FastAPI + Pydantic v2 contract models + SQLModel services.
  - **Domain Layer:** Python service modules mirroring CLI business rules.
  - **Persistence Layer:** PostgreSQL on Neon with Alembic migrations and immutable schemas per spec.

---

## 2. Core Principles

### Principle 1: Spec-First Execution
No code is authored without an approved spec. Each deliverable must reference the governing spec section and document review checkpoints before implementation begins.

**Rationale:** Ensures every artifact maps to user intent and keeps governance auditable.

### Principle 2: Agent-Generated Code Only
All code, migrations, and configuration are generated by authorized AI agents via Spec-Kit Plus workflows. Manual edits are prohibited unless a spec explicitly authorizes a human patch (rare, must be documented).

**Rationale:** Guarantees repeatability, code provenance, and auditability of every change.

### Principle 3: Phase I Logic Parity
Every Phase I CLI command (add, list, complete, update, delete) must exist with identical validation, side-effects, and error semantics across the UI, API, and Domain layers in Phase II.

**Rationale:** Maintains business correctness while evolving delivery channels.

### Principle 4: Clean Architecture Separation
UI, API, Domain, and Persistence layers MUST remain isolated:
- UI handles rendering, routing, and typed form submission only.
- API exposes typed HTTP contracts and orchestrates domain calls.
- Domain encapsulates todo rules, status transitions, and invariants.
- Persistence manages Neon access via repositories and migrations.

**Rationale:** Enables independent testing, scaling, and substitution of layers.

### Principle 5: Deterministic Typed Contracts
All inputs/outputs MUST be strongly typed:
- Next.js components rely on shared TypeScript types.
- FastAPI endpoints use Pydantic models with explicit enums and unions.
- Domain services return deterministic dataclasses/DTOs.
- Errors employ a codified taxonomy (400 validation, 404 missing todo, 409 conflict, 500 internal).

**Rationale:** Typed contracts eliminate ambiguity and guarantee reproducibility across environments.

### Principle 6: Neon PostgreSQL Persistence
Todo data is persisted exclusively in Neon PostgreSQL:
- SQLModel represents schemas.
- Alembic migrations are versioned and reversible.
- Connections use Neon connection pooling best practices.
- No alternate stores (files, SQLite, in-memory) may be introduced.

**Rationale:** Provides production-ready durability and consistent infra expectations.

### Principle 7: Reviewable Artifacts at Every Step
Each Spec, Plan, Tasks document, code diff, and migration must be reviewable independently with traceable acceptance criteria and links back to the governing spec.

**Rationale:** Sustains transparency and unlocks step-wise approvals.

### Principle 8: Production-Ready Delivery
All outputs MUST be deployable:
- Next.js and FastAPI projects adopt production configs (env separation, logging, health checks).
- Observability hooks (structured logs, tracing stubs) are included per spec.
- CI enforces formatting, linting, type-checking, tests, and database migrations.

**Rationale:** Prevents throwaway prototypes and shortens path to release.

## 3. Phase II Constraints

### Architecture Stack Boundaries
- **UI:** Next.js App Router, Server Actions for mutations, client components for interactivity, Zod schema validation before submits.
- **API:** FastAPI routers grouped by todo capability; Pydantic models reused between UI and API via shared packages.
- **Domain:** Python services that encapsulate todo logic identical to Phase I core, ensuring deterministic behavior.
- **Persistence:** SQLModel entities + repository layer; Alembic migration history checked into repo; Neon branch references captured in infra docs.

### Logic Parity & Mapping Rules
- Each CLI command maps to:
  1. A FastAPI endpoint (RESTful) mirroring arguments, defaults, and validation.
  2. A Next.js UI workflow (page, form, or mutation) with identical constraints.
  3. Domain service functions that are 1:1 ports of Phase I core modules.
- ID generation remains deterministic (UUIDv7 or increment defined in spec) and never delegated to clients.

### Contract & Type Requirements
- UI ↔ API interactions share OpenAPI-generated clients or shared TypeScript types.
- Error responses standardized: `{ code: string, message: string, details?: object }`.
- Temporal data uses ISO 8601 strings with timezone awareness.

### Testing & Reviewability
- Unit tests: domain services and repositories.
- Integration tests: FastAPI endpoints + Neon test schema.
- E2E tests: Next.js flows hitting deployed API (Playwright preferred).
- Contract tests: OpenAPI schema diff enforced per PR.

### Out of Scope (Phase II)
- No alternate data stores or caches.
- No AI/agent features (reserved for Phase III).
- No manual database access outside migrations.
- No CLI regressions; CLI remains reference implementation but is not modified beyond necessary shared logic extraction.

## 4. Evolutionary Phases
1. **Phase I:** In-memory CLI (Complete, serves as canonical logic reference).
2. **Phase II:** Full-stack web app (Current phase, governed by this constitution).
3. **Phase III:** AI-enabled assistants (future, not yet authorized).
4. **Phase IV:** Local Kubernetes deployment.
5. **Phase V:** Cloud-native expansion with eventing & multi-region.

Phase transitions require explicit constitutional review.

---

## 5. Success Criteria (Phase II)
- UI provides add/list/update/complete/delete workflows with optimistic states and server validation feedback.
- FastAPI exposes `/todos` CRUD endpoints plus list filters, returning typed payloads and structured errors.
- Domain services enforce invariants (e.g., cannot complete already completed todo) identically to Phase I behavior.
- PostgreSQL Neon stores todos with created/updated timestamps, status enums, and optional priority fields.
- Observability: request/response logging with correlation IDs; health and readiness endpoints.
- CI pipeline runs lint (ruff/eslint), type checks (mypy/tsc), tests (pytest/playwright), and migration dry-runs before merge.

## 6. Development Governance

### Core Rules
- Every task references its spec section and acceptance criteria.
- Generated code must cite the command/tool that produced it.
- Blocking violations (missing spec, manual edits, skipped reviews) halt implementation until resolved.
- Deterministic behavior enforced through typed contracts and reproducible migrations.

### Amendment Procedure
1. Propose changes via `/sp.constitution` with rationale per principle.
2. Determine semantic version bump:
   - **MAJOR:** Governance/principle removals or fundamental redefinitions.
   - **MINOR:** New principles or material expansions.
   - **PATCH:** Clarifications or non-semantic fixes.
3. Include Sync Impact Report covering templates and artifacts touched.
4. Obtain approval before downstream specs/plans/tasks proceed.

### Compliance Review
- Constitution status checked before generating specs or plans.
- `/sp.plan` must include a "Constitution Check" summarizing adherence to principles 1–8.
- Plans, tasks, and implementations referencing outdated constitutions are invalidated until revalidated.

## 7. Architectural Principles
- **Spec Is Authority:** Fix the spec, not ad-hoc code, when behavior is wrong.
- **Feature Isolation:** One feature per spec directory; no cross-feature coupling without a shared spec.
- **Phase Lock:** Complete Phase II milestones before requesting Phase III work.
- **Smallest Viable Diff:** Only touch files required for the current task; avoid speculative abstractions.
- **Typed Boundaries:** Enforce shared schemas across UI/API/Domain/Persistence to guarantee determinism.

---

## 8. Minimum Acceptance Criteria (Per Feature)
- Clear, testable acceptance criteria documented in spec and referenced in tasks.
- Explicit error paths, typed contracts, and constraint handling described before coding.
- Change set remains minimal and fully generated; no unrelated edits enter the diff.
- Code references (path:line) accompany design reviews and summaries.
- Tests (unit, integration, e2e as applicable) demonstrate correctness and run in CI.
