# Project Constitution: Multi-Phase Todo Application

## 1. Project Identity
- **Project Name:** Multi-Phase Todo Application
- **Theme:** Incremental evolution from CLI to Full-Stack to AI to Cloud-Native
- **Development Style:** Spec-Driven Development (SDD) using Spec-Kit Plus
- **Workflow Enforcement:** Specify → Plan → Tasks → Implement
- **Execution Governance:** Claude Code using Spec-Kit Plus
- **Technologies:**
  - Phase I: Python Console (CLI)
  - Phase II: Next.js + FastAPI + SQLModel + Neon DB
  - Phase III: OpenAI ChatKit, Agents SDK, MCP
  - Phase IV: Docker, Minikube, Helm
  - Phase V: Kafka, Dapr, DigitalOcean DOKS

---

## 2. Core Principles

### Principle 1: Specification-Driven Development
All functionality MUST be derived strictly from approved specs. No features beyond the scope of the active phase. The specification is the single source of truth for behavior. All code MUST be generated by agents; no manual coding by humans.

**Rationale:** Ensures alignment between user intent and implementation, prevents scope creep, and enables traceable development.

### Principle 2: Deterministic CLI Behavior
CLI commands MUST be explicit, predictable, and validated via argparse. All inputs MUST be validated, and errors MUST be handled gracefully with clear console messages. Silent failures are prohibited.

**Rationale:** Predictable behavior builds user trust and enables reliable testing.

### Principle 3: Clean Separation of Concerns
Architecture MUST maintain clear boundaries:
- `src/cli` → User interaction layer
- `src/core` → Business logic layer
- `src/utils` → Shared utility functions

**Rationale:** Separation enables testing, maintenance, and future phase isolation.

### Principle 4: Simplicity and Correctness Over Premature Optimization
Code MUST be readable, modular, and beginner-friendly. Choose the simplest correct solution first; optimize only when metrics demand it.

**Rationale:** Simplicity reduces bugs, improves maintainability, and aligns with the learning focus of this project.

### Principle 5: Forward Compatibility with Future Phases
Phase I implementation decisions MUST NOT be influenced by future phase requirements. Each phase is isolated, incremental, and spec-gated.

**Rationale:** Prevents over-engineering and ensures each phase remains focused on its specific goals.

## 3. Phase I Constraints

### Storage
- In-memory only (Python data structures)
- No database, no files unless explicitly specified
- Data resets on application restart

### Interface
- Console-based CLI application
- Entry point: `python -m src.cli.main`

### Architecture
- `src/cli` → User interaction layer
- `src/core` → Business logic layer
- `src/utils` → Shared utility functions

### Testing Requirements
- Unit tests for core logic
- Integration tests for CLI commands
- All tests MUST pass before phase completion

### Out of Scope (Phase I)
- No web UI
- No APIs
- No AI features
- No persistence layer

---

## 4. Evolutionary Phases

1. **Phase I:** Core Essentials (In-Memory Python Console Todo Application)
2. **Phase II:** Full-Stack Web App (Next.js + FastAPI + SQLModel + Neon DB)
3. **Phase III:** AI-Powered Todo Chatbot (OpenAI ChatKit, Agents SDK, MCP)
4. **Phase IV:** Local Kubernetes Deployment (Docker, Minikube, Helm)
5. **Phase V:** Advanced Cloud Deployment (Kafka, Dapr, DigitalOcean DOKS)

---

## 5. Success Criteria (Phase I)

### CLI Commands Supported
- **add**: Create new tasks with optional priority
- **list**: Display all tasks with their status
- **complete**: Mark tasks as done
- **update**: Modify existing task details
- **delete**: Remove tasks from the list

### Task Requirements
- Tasks MUST have deterministic IDs (e.g., incrementing integers)
- Tasks MAY have optional priority values
- Task IDs MUST remain stable during the session

### Quality Standards
- All tests pass (unit + integration)
- Unsupported commands are rejected correctly with clear error messages
- Application runs fully via `python -m src.cli.main`
- Phase I output is demonstrable via console commands

---

## 6. Development Governance

### Core Development Rules
- No code without a traceable task reference
- No task implementation without approved specification
- All code MUST be traceable to spec files
- Implementation MUST be blocked if constitution is missing or outdated
- All steps MUST follow SDD governance
- Code MUST be deterministic and reference existing code precisely

### Amendment Procedure
1. Submit changes via `/sp.constitution` command
2. Changes MUST include rationale for each principle modified
3. Version increment rules:
   - **MAJOR**: Backward incompatible governance/principle removals
   - **MINOR**: New principle or materially expanded guidance
   - **PATCH**: Clarifications, wording, typo fixes
4. Sync Impact Report MUST accompany all amendments

### Compliance Review
- Constitution status MUST be verified before each phase begins
- Phase gates require constitution alignment check
- Template consistency MUST be validated after amendments

---

## 7. Architectural Principles

### Spec is Authority
Refine the spec if the output is wrong, never the implementation.

### Feature Isolation
One feature = one spec file.

### Phase Lock
Complete each phase before moving to the next. No skipping phases.

### Smallest Viable Diff
Only edit what is required for the current task.

- Clear, testable acceptance criteria explicitly stated
- Explicit error paths and constraints documented
- Smallest viable change; no unrelated edits
- Code references to modified/inspected files included
- Tests define correctness
